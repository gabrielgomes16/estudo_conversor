Ao final dos 9 módulos você deve conseguir projetar, escrever e testar sozinho um conversor IFC2x3 → IFC4x3 e, depois, exportadores de IFC para outros softwares. Antes de escrever código, escreva em uma frase o que o script deve fazer, qual é a entrada e qual é a saída. Se não conseguir, ainda não entendeu o problema.

Fundamentos de BIM e do padrão IFC

BIM é o processo; IFC é o formato neutro que permite que softwares diferentes troquem esse modelo. Um conversor só é bom se preservar informação, não apenas geometria.

Conceitos-chave

  • BIM: modelo de objetos com identidade (GUID), tipo, propriedades, relações e geometria. Uma parede "sabe" que é parede, em que pavimento está e de que material é feita.
  • openBIM e buildingSMART: a buildingSMART International mantém os padrões abertos: IFC (dados), IDS (requisitos), BCF (comunicação de problemas) e bSDD (dicionário de classificações).
  • IFC = ISO 16739-1 (no Brasil, NBR ISO 16739). O IFC 4.3 virou ISO 16739-1:2024 e adicionou infraestrutura: rodovias, ferrovias, pontes, portos.
  • Versões que você vai encontrar: IFC2X3 (2005/2007, ainda muito exportado), IFC4 (2013, ADD2 TC1), IFC4X3_ADD2 (atual).
  • MVD (Model View Definition): um recorte do schema para um uso. O seu Duplex declara CoordinationView no cabeçalho; o FZK-Haus deixa a view principal vazia e lista só add-ons (QuantityTakeOff, SpaceBoundary). O MVD diz o que o arquivo deveria conter.
  • Interoperabilidade é perda controlada: todo exportador (Revit, ARCHICAD, TQS, Eberick) faz escolhas. O seu trabalho é tornar essas perdas explícitas e rastreáveis.

Leitura obrigatória

  • APOSTILA_MANIPULACAO_IFC.pdf, cap. 1 (Fundamentos openBIM, p. 28–40).
  • IFC_4x3_Resumo.pdf, seções 1 e 2.
  • buildingSMART — IFC e IFC schema specifications: a página que lista todas as versões oficiais.

Anatomia de um arquivo IFC

Um .ifc é um grafo serializado em texto (STEP Physical File, ISO 10303-21): cada linha é uma instância #id, e os atributos são lidos pela posição, nunca pelo nome. A ordem dos atributos é definida pelo schema (EXPRESS, ISO 10303-11).

Exemplo real do seu Ifc2s3_Duplex_Electrical.ifc

#22851=IfcFlowTerminal('1K7eM1Qof1dOc9$mY9I4Ci',#61,'M_Refrigerator:850 x 760mm:850 x 760mm:575374',$,'850 x 760mm',#22850,#22845,'575374');
#61=IfcOwnerHistory(#60,#2,$,.NOCHANGE.,$,$,$,0);
#22850=IfcLocalPlacement(#68,#22849);
#22845=IfcProductDefinitionShape($,$,(#22840,#22843));
#22911=IfcRelDefinesByProperties('3dFTTBnQ14v8Vcxxu42G2i',#61,$,$,(#22851),#22909);
#22909=IfcPropertySet('28aAyIEjz0rQnE7e8P1QuR',#61,'Constraints',$,(#22852,#22861,#22864));
PosiçãoAtributo (IfcFlowTerminal, IFC2X3)ValorTipo de valor
0GlobalId'1K7eM1Qof1dOc9$mY9I4Ci'string de 22 caracteres (GUID comprimido)
1OwnerHistory#61referência a outra instância
2Name'M_Refrigerator:...'string (nome típico de família do Revit)
3Description$opcional não preenchido
4ObjectType'850 x 760mm'string
5ObjectPlacement#22850referência ao posicionamento
6Representation#22845referência à geometria
7Tag'575374'id do elemento no software de origem

Outras notações: .NOCHANGE. é enumeração, (#a,#b) é lista, * é atributo derivado, IFCLABEL('x') é valor tipado (select).

Repare: a geladeira não aponta para as suas propriedades. É a relação #22911 que aponta para a geladeira e para o Pset. Isso é o que chamamos de relação objetificada, tema do Módulo 4.

Leitura obrigatória

  • IFC2X3_Esquema_Explicado.pdf, seções 3 e 6 ("Como ler EXPRESS" e "Atributos: a ordem é tudo").
  • Documentação da entidade na fonte: IfcFlowTerminal no IFC 4.3. Aprenda a navegar essa documentação: é a que você mais vai consultar.

IfcOpenShell essencial

O IfcOpenShell tem três camadas, e saber qual usar é metade do trabalho: o núcleo (file, entity_instance), os utilitários (ifcopenshell.util.*, só leitura) e a API (ifcopenshell.api, escrita segura que mantém o modelo consistente).

NecessidadeFerramentaExemplo
Abrir / salvarnúcleoifcopenshell.open(p), model.write(p), ifcopenshell.file(schema="IFC4X3_ADD2")
Buscar por classenúcleomodel.by_type("IfcWall") (inclui subtipos: IfcWallStandardCase)
Buscar por id / GUIDnúcleomodel.by_id(22851), model.by_guid("1K7e...")
Quem aponta para mim?núcleomodel.get_inverse(entity) e atributos inversos (wall.IsDefinedBy)
Percorrer o grafo para frentenúcleomodel.traverse(entity)
Ler Psets, tipo, containerutilifcopenshell.util.element.get_psets, get_type, get_container
Consultar o schemautil / wrapperifcopenshell.util.schema, ifcopenshell_wrapper.schema_by_name
Criar ou editar dadosapiifcopenshell.api.run("pset.add_pset", ...) (já usado no seu duplex_pset.py)

Conceito importante: entity_instance. Não é um objeto Python comum. É um ponteiro para a estrutura C++ do arquivo. Duas consequências: (1) uma instância pertence a um arquivo; para levar a outro você usa new_file.add(entity); (2) remover com model.remove() pode deixar referências órfãs. Prefira ifcopenshell.api.run("root.remove_product", ...).

Estrutura espacial, relacionamentos e propriedades

No IFC, quase toda ligação entre objetos é uma entidade IfcRel* separada. Quem domina meia dúzia de relações consegue navegar qualquer modelo, e quem escreve um conversor precisa recriá-las todas.

RelaçãoLigaPergunta que respondeInverso no elemento
IfcRelAggregatestodo → partes (Projeto → Terreno → Edifício → Pavimento)"De que é feito?"Decomposes, IsDecomposedBy
IfcRelContainedInSpatialStructurepavimento → elementos"Em que pavimento está?"ContainedInStructure
IfcRelDefinesByPropertieselementos → Pset ou Qto"Quais propriedades tem?"IsDefinedBy
IfcRelDefinesByTypeelementos → tipo"De que tipo é?"IsDefinedBy (2x3) / IsTypedBy (4+)
IfcRelAssociatesMaterialelementos → material"De que é feito fisicamente?"HasAssociations
IfcRelVoidsElement / IfcRelFillsElementparede → abertura → porta"Onde está o furo e o que o preenche?"HasOpenings, FillsVoids

Repare na linha IfcRelDefinesByType: no IFC2X3 o tipo vem pelo mesmo inverso dos Psets; no IFC4 ganhou um inverso próprio. Esse é o primeiro exemplo concreto de diferença de schema que o seu conversor vai enfrentar.

Propriedades: IfcPropertySet contém IfcPropertySingleValue (e outros tipos de propriedade). Psets com prefixo Pset_ são padronizados pela buildingSMART; os demais (como Constraints e Other do Duplex, vindos do Revit) são do fornecedor. Quantidades ficam em IfcElementQuantity (Qto_*).

Leitura obrigatória

  • APOSTILA_MANIPULACAO_IFC.pdf, cap. 4 (p. 77–93) e cap. 5 (p. 94–113).
  • Documentação IFC 4.3 — capítulo 4 "Concept templates", item Object Composition / Spatial Decomposition, e a seção "Concepts" de qualquer entidade na documentação oficial.

Geometria, placements e representações

A geometria IFC é implícita e relativa: um perfil extrudado posicionado em relação ao pavimento, que está em relação ao edifício, e assim por diante. Converter entre schemas preserva essa descrição; exportar para OBJ/glTF a transforma em triângulos.

Cadeia de posicionamento: IfcLocalPlacement(PlacementRelTo, RelativePlacement). No exemplo do Módulo 2, #22850=IfcLocalPlacement(#68,#22849): a geladeira é posicionada relativa a #68. A posição absoluta é o produto das matrizes da cadeia, o que use-world-coords faz por você no seu conversor.py.

Representações: IfcProductDefinitionShape → lista de IfcShapeRepresentation, cada uma com um identificador (Body, Axis, Box, FootPrint) e um tipo (SweptSolid, Brep, MappedRepresentation, Clipping...). A geladeira tem duas (#22840, #22843).

Revisão do seu conversor.py (gerado por IA, lido por você)

  • Pontos fortes: uso do iterator multiprocessado em vez de create_shape por elemento; exclusão de IfcOpeningElement e IfcSpace; offset global de índices do OBJ; GUID como nome do objeto (rastreabilidade). Exercício: explique por escrito por que cada uma é a escolha certa; onde não souber, está o seu estudo.
  • Ponto de atenção 1: shape.geometry.verts de cada elemento está em metros ou na unidade do projeto? Verifique settings e ifcopenshell.util.unit.calculate_unit_scale.
  • Ponto de atenção 2: coordenadas georreferenciadas grandes (UTM, 7 dígitos) perdem precisão em float32 nos visualizadores. Pesquise a opção de offset do modelo no IfcOpenShell.
  • Ponto de atenção 3: o script mistura leitura, transformação e escrita numa função de 120 linhas. No Módulo 9 vamos separar isso em camadas.

  • APOSTILA_MANIPULACAO_IFC.pdf: capítulo de geometria (consulte o sumário, p. 2–6).

Diferenças entre IFC2x3, IFC4 e IFC4x3

Um conversor de schema é, no fundo, uma tabela de regras de mapeamento aplicada a cada instância do grafo. Este módulo é sobre descobrir essas regras por código, não decorá-las.

Números verificados no seu ambiente (IfcOpenShell 0.9.0)

SchemaEntidadesObservação
IFC2X3653120 delas não existem no IFC4X3_ADD2
IFC4776ponte entre as duas gerações
IFC4X3_ADD2876inclui infraestrutura

No seu Duplex, a única classe usada que deixou de existir é IfcPresentationStyleAssignment (estilos de cor). Isso parece pouco, mas as mudanças mais perigosas não são classes removidas, são atributos que mudaram:

ClasseAtributos 2X3 → 4X3O que muda para o conversor
IfcWall8 → 9ganha PredefinedType (preencher com NOTDEFINED ou inferir)
IfcDoor10 → 13ganha PredefinedType, OperationType, UserDefinedOperationType; o IfcDoorStyle vira IfcDoorType
IfcOwnerHistory8 → 8mesmos nomes, mas a obrigatoriedade muda (não basta comparar nomes)
IfcFlowTerminal8 → 8igual, mas no IFC4+ o uso correto é um dos 16 subtipos, ex.: IfcElectricAppliance com PredefinedType = REFRIGERATOR

A última linha é a chave do negócio: um conversor sintático leva a geladeira para IfcFlowTerminal e o arquivo fica válido. Um conversor semântico reconhece que ela é um IfcElectricAppliance.REFRIGERATOR. O primeiro você constrói no Módulo 7; o segundo é onde você gera valor para a empresa.

Observação

O IfcOpenShell já tem ifcopenshell.util.schema.Migrator, usado pela receita Migrate do ifcpatch. Ele carrega tabelas JSON de mapeamento (class_2x3_to_4.json, attribute_4x3_to_4.json) e valores padrão para atributos novos obrigatórios. Não vamos ignorar isso. Um sênior nunca reescreve do zero o que a comunidade mantém; ele estuda, entende os limites e constrói em cima.

Leitura obrigatória

  • IFC_4x3_Resumo.pdf, seção 8 (tabela 2x3 × 4.3) e seção 10 (armadilhas).
  • IFC2X3_Esquema_Explicado.pdf, seção 13 (o que muda no 4.3).
  • IFC4 — Change log (anexo de mudanças) e IFC 4.3 — Change log (anexo F).
  • O código-fonte do Migrator: abra .venvifc/lib/python3.13/site-packages/ifcopenshell/util/schema.py e leia a classe inteira. Sim, ler código dos outros é estudo.

  tests/

    test_migrador.py

Por que essa separação? O cli.py não sabe nada de IFC, então depois vira uma API web sem mudar o resto. As regras ficam em dados (.csv), então um engenheiro civil pode corrigir um mapeamento sem programar. Esse é o pensamento de arquitetura que quero que você desenvolva.

7.1 Decisão: construir sobre o Migrator

Decisão tomada em 05/10/2026: o conversor estende ifcopenshell.util.schema.Migrator, sem reescrevê-lo. Uma sondagem no Duplex mostrou três fatos que guiam as etapas:

  • Dois saltos, não um. O Migrator só tem tabelas de mapeamento para IFC2X3 ↔ IFC4 e IFC4 ↔ IFC4X3. Não existe tabela direta 2X3 → 4X3, então o caminho passa obrigatoriamente pelo IFC4.
  • As perdas não geram erro. No Duplex, nenhum dos saltos levantou exceção. As perdas aparecem apenas como mensagens print ("Unable to find equivalent attribute", "Failed to generate default value"). Arquivo gerado não significa arquivo correto. Capturar essas mensagens é o trabalho do relatorio.py.
  • Saída possivelmente inválida. No segundo salto, algumas IfcRelSpaceBoundary ficaram sem um atributo obrigatório. Isso precisa de regra própria (etapa 5) e de validação (Módulo 8).

7.2 Etapas

  1. Requisitos e casos de teste. Escreva REQUISITOS.md: entrada, saída, o que é "conversão correta" (mesmo número de produtos? mesmos GUIDs? mesmos Psets?). Defina 3 critérios mensuráveis. Sem isso não há como testar.
  2. Esqueleto + relatório de entrada. cli.py + leitor.py: recebe o arquivo, recusa se não for IFC2X3, imprime o inventário do Módulo 3. Nenhuma conversão ainda.
  3. Cópia com o Migrator. Migrator().migrate(inst, destino): faça a conversão em dois saltos (IFC2X3 → IFC4 → IFC4X3_ADD2). Em cada salto: crie o arquivo de destino vazio, chame preprocess(origem, destino) e migre cada instância. O Migrator copia atributos por nome (ou pela tabela attributes_mapping) e segue as referências sozinho. O cache (dict id antigo → id novo; no Migrator, migrated_ids) evita duplicar #61 (OwnerHistory) mil vezes. Rode no Duplex e colecione erros e avisos: cada exceção ou mensagem impressa pelo Migrator (capture o stdout com contextlib.redirect_stdout) é uma regra que falta.
  4. Regras por cima (subclasse). class MigradorProjeto(Migrator): sobrescreva migrate_class para consultar a sua tabela antes de chamar super(), e generate_default_value para os valores padrão da empresa; use attribute_overrides para valores pontuais. Atributo removido: o Migrator descarta em silêncio, então compare os atributos de origem e destino e registre no relatório. Use o CSV do Módulo 6 como fonte.
  5. Casos especiais. Primeiro teste o que o Migrator já resolve: preprocess trata IfcCalendarDate; confira IfcPresentationStyleAssignment (o único do Duplex) e IfcDoorStyle → IfcDoorType. Só escreva função própria, com teste, para o que falhar ou sair errado.
  6. Camada semântica (opcional, liga por --semantico). Lê mapeamento_semantico.csv e reclassifica IfcFlowTerminal para o subtipo correto com PredefinedType. Dica: ifcopenshell.util.schema.reassign_class existe.
  7. Relatório e comparação. Gere um relatório (Markdown ou HTML) com contagens antes/depois, regras aplicadas e perdas. Depois rode a receita Migrate do ifcpatch (o Migrator puro) no mesmo arquivo e compare: toda diferença tem de vir de uma regra sua no CSV. Diferença sem regra é bug.

Assinaturas para começar (o corpo é com você):

# migrador.py
from ifcopenshell.util.schema import Migrator

class MigradorProjeto(Migrator):
    def __init__(self, regras: Regras, relatorio: Relatorio): ...  # chame super().__init__()
    def migrate_class(self, element, new_file): ...             # tabela própria antes do super()
    def generate_default_value(self, attribute, new_file): ...  # padrões da empresa

Atenção

Esquecer preprocess antes do laço; copiar código do Migrator em vez de sobrescrever um método; engolir exceções sem registrar no relatório; perder GUIDs; não conferir o que o Migrator descartou em silêncio (atributos e enumerações sem equivalente).

Qualidade: testes, validação e IDS

Um conversor que "abre no visualizador" não está testado. Você precisa de quatro níveis de verificação, do mais barato ao mais caro:

NívelPerguntaFerramenta
UnitárioEsta regra converte este caso pequeno corretamente?pytest + IFCs mínimos criados em código
SchemaO arquivo de saída obedece ao EXPRESS do IFC4X3?python -m ifcopenshell.validate saida.ifc e o bSI Validation Service
InformaçãoOs dados que o cliente exige continuam lá?ifctester + arquivo IDS
RegressãoO que mudou entre entrada e saída?comparação por GUID (ou ifcdiff)

Testes de propriedade (invariantes) são os mais valiosos num conversor. Exemplos: todo GUID de IfcProduct da entrada existe na saída; o número de Psets por elemento não diminui; todo elemento continua no mesmo pavimento. Escreva-os uma vez e eles protegem todas as futuras mudanças.

IDS (Information Delivery Specification) é o padrão buildingSMART para escrever "o que um modelo deve conter" em XML: por exemplo, "toda IfcWall deve ter Pset_WallCommon.IsExternal". É a ponte entre o que os engenheiros sabem e o que o código verifica.

Leitura obrigatória

  • pytest — Get started e o conceito de fixtures.
  • IfcTester e buildingSMART IDS.
  • APOSTILA_MANIPULACAO_IFC.pdf: capítulo sobre IDS (consulte o sumário).

Exercícios

  1. Instale pytest e ifctester no .venvifc. Escreva uma fixture que cria em memória um IFC2X3 mínimo (projeto, pavimento, uma parede com Pset) com ifcopenshell.api. Use-a em 3 testes do seu migrador.
  2. Implemente os 3 invariantes acima como testes que rodam no Duplex completo.
  3. Rode ifcopenshell.validate na saída do seu conversor e na saída do ifcpatch Migrate. Compare a quantidade e o tipo de erros.
  4. Junto com um engenheiro da empresa, escreva um IDS com 5 requisitos reais de um projeto de vocês. Rode com ifctester antes e depois da conversão.
  5. Envie um arquivo convertido ao Validation Service da buildingSMART e leia o relatório inteiro.

Conversão de IFC para outros softwares

Todo exportador segue o mesmo padrão: extrair do IFC para um modelo intermediário seu (classes Python simples), transformar (unidades, eixos, filtros) e escrever no formato de destino. Com isso, cada novo software custa só um novo escritor.
